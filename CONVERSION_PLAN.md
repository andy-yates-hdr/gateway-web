# Conversion plan: WordPress+GraphQL → Markdown content in gateway-web

This is the document `SPEC.md` asks for: how WordPress rendering currently works in `gateway-web`, how well the `cms_spike/content` Markdown aligns with it, and how the conversion is enacted as a spike.

## How WordPress rendering works today

`gateway-web` (Next.js App Router) has a single data-access layer, `src/utils/cms.ts`. It POSTs hand-written GraphQL query strings (`src/config/queries/*.ts`, no client library, no codegen) to `NEXT_PUBLIC_WORDPRESS_API_URL` via a `fetchCMS()` helper, with 10s ISR (`next: { revalidate: 10 }`), and exposes ~25 getter functions. Every consuming page/component imports from `@/utils/cms` — none call GraphQL directly. Many "specific" getters (`getWorkWithUs`, `getDataCustodians`, `getPatientsAndPublic`, `getGlossary`, `getGettingStarted`, `getMetadataOnboarding`, `getOpenSourceDevelopment`, `getPrivacyPolicy`, `getCookieNotice`, `getResearchersInnovators`, `getTechnologyEcosystem`, `getTermsAndConditions`, `getHowToSearchPage`) are thin wrappers around `getContentPageQuery(name, {id, idType: "URI"})` with a hardcoded slug.

Rendering is uniform: a page fetches `{ id, title, content, slug?, categories? }` (`PageTemplateDefault`) and passes `content` (a WordPress-rendered HTML string) to the shared `src/components/HTMLContent/HTMLContent.tsx`, which sanitizes it with `isomorphic-dompurify` and injects it via `dangerouslySetInnerHTML`.

`gateway-2-wordpress` (the WP checkout in this repo) contains no application code — no ACF field group JSON, no custom post types/taxonomies, no theme. All real content and ACF schema live only in the live WordPress database, which this repo cannot reach. So the only concrete schema available to build against is what `gateway-web` already expects (`src/interfaces/*.ts`), not the live WordPress fields.

## How well `cms_spike/content` aligns

`cms_spike/content` was crawled from the real healthdatagateway.org site (67 pages, news, events, releases). Comparing its schema (`cms_spike/src/content.config.ts`) to `gateway-web`'s expectations:

| gateway-web shape | cms_spike/content equivalent | Alignment |
|---|---|---|
| `PageTemplateDefault` (`id`, `title`, `content` HTML, `slug`, `categories`) | `content/pages/**/*.md` (`title`, `description`, `draft`, `source_url`, `crawled`, `needs_authoring` + Markdown body) | **Good.** Title and body map directly; `content` becomes rendered Markdown→HTML. No `categories` equivalent, but the field is optional/unused outside news/events. |
| Parent/child pages (`getContentPageByParentQuery`) | `content/pages/support/**`, `content/pages/data-custodian/**` (nested directories, some 2 levels deep, e.g. `support/data-access-request/manage-dar.md`) | **Good.** The route structure and the crawled directory structure already mirror each other. |
| `NewsNode`/`EventNode` (`newsFields.headline/date/text/link.url/image.node.mediaItemUrl`) | `content/news/**`, `content/events/**` (`title`, `date`, `excerpt`, `external_url`, `source`, `image` + body) | **Good**, with a rename: `title→headline`, `excerpt→text`, `external_url→link.url`, `image→image.node.mediaItemUrl`. |
| `ReleaseNode` (`title`, `date`, `content`, `release.releaseDate`) | `content/releases/**` (`title`, `date`, `description` + body) | **Good.** `release.releaseDate` is a duplicate of `date`, needed because `getReleaseByYear` filters on it. |
| Homepage `PageTemplateHome` (ACF `homeFields`: video, logos, newsletter copy; `meetTheTeam` ACF block) | *none* | **Poor.** No ACF-equivalent content was crawled — this content lives in structured ACF fields on the live site, not in prose pages. |
| Cohort Discovery promo/step templates (`promofields`, `newCohortDiscoveryFieldGroup` — paginated step arrays with CTAs/media) | *none* | **Poor.** Same reason — bespoke ACF field groups per page, not crawlable as prose. |
| Meet the Team / Contributors & Collaborators (ACF repeater `teamList[{info,name,jobTitle,image}]`) | `content/team.yaml` (flat `people` list: `name`, `role`, `photo`, `group`) | **Partial.** Structurally similar (a list of people) but field names and grouping semantics differ enough that mapping it faithfully is out of scope for this spike. |

**Conclusion**: plain prose content (static pages, news, events, releases) aligns well and is safe to convert. ACF-structured templates (homepage, Cohort Discovery, team repeaters) have no source data outside the live WordPress database and are left untouched.

## Scope of this spike

**Converted to Markdown** (behind the feature flag below): `getContentPageQuery`, `getContentPageByParentQuery`, `getContentPostQuery`, `getNews`, `getEvents`, `getReleaseNotes`, `getMissionAndPurposes` — and by extension every thin wrapper page/getter that calls `getContentPageQuery` internally.

**Left calling WordPress unchanged, documented gap**: `getHomePageBanner`, `getMeetTheTeam`, `getContributorsAndCollaborators`, `getCohortDiscovery`, `getNewCohortDiscovery`, `getCohortDiscoverySupportPageQuery`, `getCohortTermsAndConditions`. Converting these would require inventing ACF-shaped content that was never crawled, which would misrepresent what this spike demonstrates.

**Partial best-effort fallback, not a real conversion**: `getHomePage`. The homepage's ACF fields (`homeFields`: hero video, affiliate link, funder logos, newsletter copy; `meetTheTeam`: the team callout) have no equivalent anywhere in the crawled Markdown, same as the "documented gap" list above — but unlike those, `getHomePage` sits on the app's root route (`layout.tsx`'s import graph means it's always reachable, and `/` is usually the very first page anyone visits), so leaving it 500ing whenever there's no real WordPress backend configured made the whole spike unusable to demo starting from `/`. `getHomePageFromMarkdown()` in `cms.ts` builds a `PageTemplateHome` with the ACF-only fields left blank/empty (safe: `HTMLVideoEmbed` and `LogoSlider` already handle an empty `gatewayVideo`/`logos`) and `posts.edges` populated with the real 4 latest news/events, same source `getNews`/`getEvents` use. Verified live: `/en` returns `200` with the real "Latest news and events" header and a real event card (image resolving through `/api/markdown-assets/...`) — not just the ACF-only sections quietly missing.

## Feature-flag gating

Gateway already has a feature-flag system and the Markdown path is gated behind it rather than replacing WordPress outright:

- **Backend**: Laravel Pennant (`gateway-api`, DB-backed store). Defaults live in `gateway-api/database/seeders/FeatureSeeder.php`'s `$defaults` array; toggled at runtime via `FeatureController` / the admin `FeatureFlagsTable` UI — not env vars.
- **Frontend**: `@vercel/flags` in `gateway-web/src/flags.ts`, one `flag({ key, adapter })` export per flag via the shared `createAPIFlagAdapter()`. Server functions `await` the flag directly, the same pattern `src/app/widgets/[slug]/page.tsx` uses for `isWidgetsEnabled`.

This spike adds `MarkdownContentSource` (default `false`). Each converted `cms.ts` function checks `await isMarkdownContentEnabled()` and branches: Markdown when enabled, the original untouched WordPress call when disabled. With the flag off, behavior is unchanged from before this spike — the WordPress code path is preserved, not just unreached by coincidence.

## Implementation

- `gateway-web/src/utils/markdownContent.ts` — reads directly from `cms_spike/content` in place (per SPEC: "those markdown documents will be hosted locally (see within `cms_spike`)"), via a hand-rolled frontmatter parser (no new dependency — `js-yaml` is only a transitive dependency of `gateway-web`, and frontmatter here is flat). `content` is left as **raw Markdown**, not HTML.
- `gateway-web/src/utils/cms.ts` — adds the flag branch described above to the seven functions listed, leaving everything else untouched.
- `gateway-web/src/components/HTMLContent/HTMLContent.tsx` — reads `isMarkdownContentEnabled` via `useFeatures()` and branches: Markdown content renders through `markdown-to-jsx` (already a direct dependency, already used elsewhere client-side in this codebase) directly; WordPress content keeps its existing `DOMPurify` + `dangerouslySetInnerHTML` path unchanged. This is the one shared rendering component every converted page already goes through, so it's still a single, small, flag-gated change rather than touching each page.
  - **Why not pre-render Markdown to an HTML string in `markdownContent.ts` instead**, so `HTMLContent` never needed touching at all? That was the first approach, using `react-dom/server`'s `renderToStaticMarkup`. It compiled and passed every unit/type/lint check, but **failed at runtime** — Next's App Router bundler rejects any module reachable from a Server Component that imports `react-dom/server` ("You're importing a component that imports react-dom/server..."), and `markdownContent.ts` is imported by `cms.ts`, which is imported by the (Server Component) page tree. This only surfaced once `npm run dev` was actually run and a converted page was requested — the lesson being that for Next App Router work specifically, booting the dev server and hitting a real route catches a class of bug that `tsc`/`eslint`/Jest cannot.
  - One direct consumer, `about/our-mission-and-purpose/page.tsx`, rendered `mission.node.content` via its own `dangerouslySetInnerHTML` rather than through `HTMLContent` — it was switched to use `HTMLContent` too, so it picks up the same Markdown/HTML branch instead of injecting raw Markdown as if it were HTML.
- A dozen more getters (`getWorkWithUs`, `getTechnologyEcosystem`, `getResearchersInnovators`, `getDataCustodians`, `getPatientsAndPublic`, `getGlossary`, `getGettingStarted`, `getMetadataOnboarding`, `getOpenSourceDevelopment`, `getPrivacyPolicy`, `getCookieNotice`) turned out to call `fetchCMS(GetContentPageQuery(...))` **directly**, not the local `getContentPageQuery` wrapper (easy to miss — `GetContentPageQuery`, the imported query-string builder, and `getContentPageQuery`, the local wrapper, differ only by the first letter's case). They were refactored to call the local wrapper instead, which is behaviourally identical on the WordPress path and means they now pick up the Markdown branch for free rather than needing their own copy of the flag check. `getTermsAndConditions` and `getHowToSearchPage` used dedicated canned queries with no `id` parameter at all; they got an explicit flag branch pointing at the matching `content/pages` slug instead.

### Known slug mismatches

Auditing every `getContentPageByParentQuery` call site turned up a third id shape beyond the two `loadPage` already handled (an exact path, or a bare filename reachable by recursive basename search): a good number of them — `"exploring-collections-data-custodians-and-data-custodian-networks"` for `/support/collections`, `"using-the-gateway-enquiry-data-access-request-module"`, `"managing-and-reviewing-submitted-data-access-requests"`, and others across `data-custodian/support/**` — are WordPress's auto-generated slug-from-title (used whenever a page's slug was never hand-tuned), which has no relationship to the crawled filename at all. `/support/collections` returning a hard 404 despite `content/pages/support/collections.md` existing was exactly this: the id doesn't match the file's path *or* its basename, only a slugified version of its **title** ("Exploring Collections, Data Custodians and Data Custodian Networks" → `exploring-collections-data-custodians-and-data-custodian-networks`).

`loadPage` now tries this as a third, last-resort fallback: slugify every page's title (lowercase, strip punctuation, spaces→hyphens) and compare against the requested id. It's the most expensive of the three lookups — it reads every page in `content/pages` rather than one file or one directory listing — so it only runs once the first two have already failed, which should be rare in practice.

This fixed every route audited above except two, which remain genuine gaps rather than false-fixed: `getGettingStarted` (`id: "data-custodian-getting-started"`, title "Getting started on the Gateway and managing your Team") and `getMetadataOnboarding` (`id: "data-custodian-metadata-onboarding"`, title "Metadata Onboarding and Integrations") — neither the filename nor a slugified title matches either id, so whatever WordPress slug they actually resolve to on the live site isn't derivable from anything in this crawled content. `loadPage` correctly falls through to `null` for both (a graceful 404 via the caller's existing `notFound()` handling), and a test (`markdownContent.test.ts`) pins down that the new fallback doesn't accidentally false-match either of them. This is exactly the kind of alignment gap the SPEC asked this document to surface, not something to paper over with a bespoke alias table for a spike.

## Sourcing content from GitHub instead of a local checkout

`markdownContent.ts` reading via `fs` from `../../cms_spike/content` only works because `cms_spike` happens to be checked out as a sibling directory on this machine — it wouldn't work in gateway-web's actual deployment, where no such sibling checkout exists. `cms_spike` is also published to a GitHub repo, `HDRUK/techspike-wordpress-replacement`, over HTTPS (currently private, so reading it needs authentication) — exactly the path SPEC.md anticipated ("those markdown documents will be hosted locally... but eventually might be pulled down from GitHub").

`markdownContent.ts` now supports both, chosen by inspecting `MARKDOWN_CONTENT_ROOT` — which is **required**, with no default, but only once actually used:

- **Not set (or blank)**: `getContentRoot()` throws — `"MARKDOWN_CONTENT_ROOT is not set..."` — rather than silently falling back to a hardcoded sibling `cms_spike/content` path (the original behaviour). That fallback meant a missing env var pointed at a specific machine's checkout without saying so; failing loudly was chosen over that. The rejection is deliberately **lazy**, not at module-import time: `cms.ts` imports `markdownContent.ts` unconditionally (and `layout.tsx` imports `cms.ts` unconditionally), but only calls into it from inside its `if (await isMarkdownContentEnabled())` branches — so an unset root only matters, and only fails, once `MarkdownContentSource` is actually on. With the flag off (its default), the module can be completely unconfigured with zero effect. (An earlier version of this validated eagerly at import time, which meant *every* page failed regardless of the flag — caught by testing the flag-off path specifically, not just assumed from reading the import graph.)
- **Set to a local filesystem path**: local `fs` mode, e.g. the sibling `cms_spike/content` checkout.
- **Set to an `http(s)://` URL**: remote mode. The URL is expected to be a GitHub Contents API URL pointing at the content directory, e.g. `https://api.github.com/repos/HDRUK/techspike-wordpress-replacement/contents/content?ref=main` — chosen over a plain `raw.githubusercontent.com` URL specifically because the Contents API's one endpoint shape does both file fetching (`Accept: application/vnd.github.raw+json` returns the raw body) and directory listing (`Accept: application/vnd.github+json` returns a JSON array of `{name, type}`) — `raw.githubusercontent.com` can only do the former, which would have broken the recursive slug fallback and collection loading. `MARKDOWN_CONTENT_GITHUB_TOKEN`, if set, is sent as `Authorization: Bearer <token>` — needed once the repo goes private, never logged.

**Verified live**, both directions: with `MarkdownContentSource` on and `MARKDOWN_CONTENT_ROOT` unset, every route 500s with the exact rejection message. With the flag switched off and the same env var still unset, pages render again — any remaining error at that point is `cms.ts`'s unrelated WordPress `fetchCMS` path failing on its own missing config, never `markdownContent.ts` (confirmed by grepping the server log for the rejection message and finding zero occurrences).

Everything above this module (`cms.ts` and every page it serves) is unaware of which mode is active; the boundary is exactly `markdownContent.ts`'s exported functions, which all became `async` to accommodate the network calls remote mode needs (previously synchronous `fs` calls).

**Checking which mode is actually live**: rendered pages look identical either way (same content, same repo), and Next doesn't log arbitrary server-side `fetch` calls by default, so neither the browser nor the terminal proves it on their own. `GET /api/markdown-content-status` reports it directly from the running process — `{ source: "github" | "local", contentRoot }` — safe to expose since `contentRoot` never contains `MARKDOWN_CONTENT_GITHUB_TOKEN` (only ever sent as a request header, never embedded in the URL). It's a debug aid for this spike; an unauthenticated config-echoing endpoint isn't a pattern to carry into production without gating it out of prod builds first.

### Caching (GitHub mode only)

Remote mode originally did one or more network calls per render (a listing call for every directory walked, plus a content call per file) — fine for a spike, not for real traffic. Rather than reuse Next's `fetch` cache (`next: { revalidate }`, the mechanism the WordPress path already uses in `fetchCMS`), `markdownContent.ts` has its own in-memory cache: an ISR-style `revalidate` option doesn't have anywhere to attach ETag-based revalidation logic, which was a specific requirement here, so a small purpose-built `fetchWithCache` wraps every remote read (file, directory listing, asset) instead. It deliberately does **not** apply to local mode — `fs` reads are already effectively instant, so there's nothing worth caching there.

Two independent, env-configured knobs:

- `MARKDOWN_CONTENT_CACHE_TTL_SECONDS` — how long a fetched value is served with no network call at all. Defaults to 300s. Set to `0` to disable caching outright (every read hits the network, matching the original behaviour).
- `MARKDOWN_CONTENT_ETAG_CHECK` — off by default. Once the TTL has expired:
  - **Off**: the expired entry is simply re-fetched unconditionally (a plain GET), same cost as no caching once the TTL lapses.
  - **On**: revalidates first via a conditional GET (`If-None-Match: <cached etag>`) rather than a separate `HEAD` — confirmed live against the real `HDRUK/techspike-wordpress-replacement` repo that GitHub's Contents API honours this and returns a `304` with no body when the content hasn't changed (same for both file and directory-listing endpoints). A `304` extends the cached entry's expiry and reuses its value, with no re-download or re-parse; any other status re-fetches and replaces the cache entry, ETag included.

On a network exception (not a clean HTTP error status — e.g. a genuine timeout or DNS failure), `fetchWithCache` falls back to a stale cached value if one exists, rather than treating a transient outage the same as a real 404. A clean `!res.ok` response (the resource genuinely doesn't exist) still returns `null` as before — only exceptions get the stale-fallback treatment.

**Verified live**, against the real repo and token (not just mocks): a cold request to `/en/how-to-search` took 1.34s; an immediately repeated request to the same page took 0.07s — consistent with the second and third requests never touching the network. Confirmed independently via GitHub's own rate-limit counter (`GET /rate_limit`): three repeated requests to the same page consumed zero additional API calls (`remaining` unchanged at 4998 across all three). Also covered by 6 new tests in `markdownContent.test.ts` — cache-hit-within-TTL, unconditional-refetch-after-TTL-with-ETag-off, TTL=0 disabling caching, 304-reuses-cache-with-ETag-on, fresh-fetch-on-changed-ETag, and stale-fallback-on-network-exception — using fake timers (`jest.setSystemTime`) to control TTL expiry deterministically rather than real delays.

### Verifying remote mode

No real token was available to test against the actual private `HDRUK/techspike-wordpress-replacement` repo, so remote mode is verified with a mocked `fetch` in `src/utils/markdownContent.test.ts` (10 tests covering both modes) — proving the exact request URLs, `Accept`/`Authorization` headers, the recursive-fallback-via-directory-listing path, collection loading, and graceful `null` on a failed request, all without any real network access or secret. Writing that test caught a real bug: the recursive basename fallback re-prefixed an already-relative path (`pages/${match}` where `match` was already `pages/about/data-custodians.md`), which would have 404'd on any nested page in both modes — fixed before it shipped.

To verify against the real repo: set `MARKDOWN_CONTENT_ROOT` to the URL above and `MARKDOWN_CONTENT_GITHUB_TOKEN` to a fine-grained PAT scoped read-only to that one repo, both directly in `.env.local` (never pasted into a prompt), then run through the same "How to run it" steps below.

## Images

Markdown content references images as site-root-relative paths, e.g. `![...](/assets/images/foo.png)` inline in a page body, or `image: /assets/images/foo.png` in news/events frontmatter — a holdover from how the `cms_spike` Astro site serves them, base-path-free. Neither gateway-web's own static files nor GitHub serve that path directly, so left alone these paths 404 (or, before this was addressed, silently rendered as broken images with no error at all, which is worse).

- `markdownContent.ts`'s `loadAsset(relativePath)` resolves an asset the same dual-mode way as everything else in that module: locally from `assets/` (a sibling of `content/`, mirroring `cms_spike`'s own layout), or remotely from the GitHub Contents API's `assets/` path in the same repo — via `Accept: application/vnd.github.raw+json`, which returns raw bytes for binary files too, not just text. Content-Type is guessed from the file extension (png/jpg/jpeg/gif/svg/webp).
- `src/app/api/markdown-assets/[...path]/route.ts` — a Next Route Handler that calls `loadAsset` and streams the bytes back with the right `Content-Type` and `Cache-Control: public, max-age=3600`. This is the one place that decides how an asset path resolves to bytes, for both local and remote mode.
- `src/utils/markdownAssetUrl.ts` — a tiny dependency-free module exporting `toPublicAssetUrl(assetPath)`, which rewrites `/assets/images/foo.png` → `/api/markdown-assets/images/foo.png` (anything not matching an `/assets/...` path is returned unchanged, so external/absolute URLs aren't touched). Kept deliberately separate from `markdownContent.ts` — that module imports `fs`, and this helper is needed in a **client** component (`HTMLContent`), so bundling it together would try to ship `fs` to the browser and break the build.
- Applied in two places, matching the two ways an image path reaches the page:
  - **Inline Markdown images** (`![alt](/assets/...)` in a page/post body): `HTMLContent.tsx`'s Markdown branch overrides `markdown-to-jsx`'s `img` renderer (`options.overrides.img.component`) to rewrite `src` through `toPublicAssetUrl` before rendering — no change to the Markdown source itself.
  - **Frontmatter `image` fields** (news/events cards): `cms.ts`'s `linkedItemsFromMarkdown` now builds `image.node.mediaItemUrl` via `toPublicAssetUrl(...)` directly, since that's a plain string prop consumed by `NewsSummaryCard`, not Markdown.

Verified live (dev server, real HTTP): `GET /api/markdown-assets/images/release-notes.png` returns the real file byte-for-byte (301,228 bytes, matching `cms_spike/assets/images/release-notes.png` exactly) with `Content-Type: image/png`; a missing asset 404s cleanly; `/en/terms-and-conditions`'s inline Markdown image and `/en/news/events?tab=news`'s card images both render through the rewritten `/api/markdown-assets/...` URLs. Also covered by 6 new mocked-`fetch` tests in `markdownContent.test.ts` (local + remote `loadAsset`, including the remote request's exact URL/headers) and 4 in `markdownAssetUrl.test.ts`.

**Not done**: remote-mode asset requests aren't cached beyond the route handler's `Cache-Control` header — same caveat as content fetches above, and the same fix (ISR-style `next: { revalidate }`) would apply to both.

## Rich Markdown: embedded videos and image captions

`cms_spike`'s Astro build had two extra behaviours, implemented as Sätteri hast plugins in `cms_spike/src/plugins/markdown-media.mjs`, that plain `markdown-to-jsx` doesn't replicate on its own — so converted pages initially regressed on them relative to the previous spike:

- A lone image with a title in a paragraph of its own — `![alt](src "A caption")`, standard CommonMark, no custom syntax — should render as a captioned `<figure>`, not a bare `<img>`. Real example: `content/pages/support/data-access-request.md`'s "Via 'Actions' on the Datasets & BioSample search" captions.
- A lone link to a YouTube URL in a paragraph of its own should render as an embedded video, not a plain link. Real example: `content/pages/how-to-search.md`'s `[Searching for Datasets & BioSamples...](https://www.youtube.com/embed/CobSWnXwCNg?feature=oembed)`.

`markdown-to-jsx` has no visitor/plugin system — its only extension point is overriding rendering per HTML tag via `options.overrides`. Both behaviours are reimplemented in `src/components/HTMLContent/MarkdownMedia.tsx` by overriding `p` (not `a`/`img` alone): the `p` override inspects its single meaningful child — filtering out whitespace-only text nodes the same way the original plugins' `meaningful()` helper did — and if that child is `MarkdownImage` with a `title` prop, or an `<a>` whose `href` matches a YouTube URL (embed/ID, watch?v=ID, or youtu.be/ID — the same three regexes ported from `youTubeId()` in the original plugin), it renders the richer markup instead of a plain paragraph. Anything else renders as an ordinary `<p>`, unchanged.

- **Captioned image** → `<figure>` wrapping the image plus a `<figcaption>` (styled via `MarkdownMedia.styles.ts`'s `Figure`/`FigureCaption`, MUI `styled()`, matching the codebase's existing convention in `HTMLContent.styles.ts`).
- **YouTube link** → `VideoFacade`, a click-to-load player carrying over the original's privacy rationale word-for-word: nothing is requested from YouTube until the reader presses play, and the poster image is served locally (via the same `markdown-assets` route as any other image, from `assets/images/video-posters/{id}.jpg` — the posters already exist in `cms_spike/assets/images/video-posters/`, fetched previously by `crawler/fetch_posters.py`) rather than from `i.ytimg.com`, which would leak the visit just the same. On click, it swaps to a real `<iframe src="https://www.youtube.com/embed/{id}">`. The link text becomes both the caption and the iframe's `title` — the same accessibility improvement over the live site's untitled iframes that the original plugin's comment called out.

Verified live against the real routes named in this exact request: `/en/how-to-search` renders both of its videos as click-to-play facades with real posters (`/api/markdown-assets/images/video-posters/CobSWnXwCNg.jpg`, byte-verified as a real 1280×720 JPEG) and the correct `aria-label`s/caption text; `/en/support/data-access-request` renders its two captioned images as `<figure>`/`<figcaption>` pairs with the real caption text ("Via 'Actions' on the Datasets & BioSample search", etc.) *and* its own embedded video, while its uncaptioned images stay plain `<img>` tags as before. Backed by 10 tests in `MarkdownMedia.test.tsx` (`youTubeId` regex cases, figure/no-figure branching, and — via `@testing-library/react`'s `fireEvent.click` — that the real iframe only appears after the play button is pressed, never before).

## Verification performed

- `tsc --noEmit` and `eslint .` across `gateway-web`: zero errors introduced (pre-existing warnings elsewhere unchanged).
- Full existing Jest suite (`npm test`, 221 suites / 782 tests) passes. Getting there required two adjustments, both needed regardless of this spike, not specific to it:
  - `jest.config.js` needed a `moduleNameMapper` entry for `@/flags` (`"^@/flags$": "<rootDir>/src/flags"`) — it had per-folder entries for every other `@/*` alias except this one, so `jest.mock("@/flags", ...)` couldn't resolve it.
  - `@vercel/flags` pulls in `jose`, which ships an ESM-only build; any test that now transitively imports `cms.ts` (which imports `@/flags`) breaks Jest's parser unless `@/flags` is mocked. `cms.test.ts`, `news/events/page.test.tsx`, and `news/releases/page.test.tsx` each got `jest.mock("@/flags", () => ({ isMarkdownContentEnabled: jest.fn().mockResolvedValue(false) }))`, preserving their existing WordPress-path assertions unchanged. (Adding `jose`/`@vercel/flags` to `transformIgnorePatterns` does not fix this — `next/jest`'s own default patterns still exclude general `node_modules` from transform regardless.)
- **The dev server was actually booted and real routes were requested** (`npm run dev`, with `isMarkdownContentEnabled` temporarily hardcoded to `true` in `src/flags.ts` for the run, then reverted). This is what caught the `react-dom/server` bundler error described above — it only surfaces at request time, not in `tsc`/`eslint`/Jest — and confirmed, against real HTTP responses:
  - `/en/terms-and-conditions` — 200, real title, and the rendered HTML contains the actual body text and `<strong>`/`<h2>` markup from `cms_spike/content/pages/terms-and-conditions.md`, with no leaked `##`/`**` Markdown syntax.
  - `/en/about/data-custodians` — 200, real title (proves the recursive basename fallback into `pages/about/`).
  - `/en/news/events?tab=news` — 200, real title.
  - `/en/support/cohort-discovery` — **500**. Not a bug: this route is served by `getCohortDiscoverySupportPageQuery`, one of the ACF-backed functions explicitly left calling WordPress (see "Scope of this spike" above), and `NEXT_PUBLIC_WORDPRESS_API_URL` was blank in the local `.env.local`, so `fetch("")` throws. It only *looks* related because `content/pages/support/cohort-discovery.md` happens to exist — that file isn't actually reachable through this URL in gateway-web today. Worth remembering when picking routes to demo: matching filenames in `cms_spike/content` don't guarantee a matching converted route.

## How to run it

1. `cd cms_spike_v2/gateway-web && npm install` (already done once in this environment).
2. Enabling the flag needs a value from Pennant/`gateway-api`, which `gatewayFlagAdapter.ts` calls over HTTP and gracefully treats as `false` if unreachable (`getFeatures()` catches fetch errors and returns `{}`) — so simply running `gateway-web` alone always takes the WordPress path, flag off, matching production default. Two ways to actually see the Markdown path:
   - **Proper way**: run `gateway-api` locally (Tilt/Helm, or `php artisan octane:frankenphp`; see its README), then `php artisan tinker` → `Laravel\Pennant\Feature::activate('MarkdownContentSource');`, and point `gateway-web`'s `.env.local` `NEXT_PUBLIC_API_V1_URL`/`NEXT_PUBLIC_API_V1_IP_URL` at it.
   - **Fast local-only demo** (what was used for the verification above): temporarily replace the `isMarkdownContentEnabled` export in `src/flags.ts` with `export const isMarkdownContentEnabled = async () => true;`, run `npm run dev`, then revert it — never commit that override.
3. `npm run dev`, then visit `http://localhost:3000` — it redirects to `/en`. Hit the converted routes directly, e.g. `http://localhost:3000/en/terms-and-conditions`, `/en/about/data-custodians`, `/en/support/cohort-discovery` (via the generic parent/child route, not the one above — check `src/app/[locale]/(logged-out)/support/**/page.tsx` files for which getter each route actually calls before assuming a URL is converted), `/en/news/events?tab=news`, `/en/news/releases`.
